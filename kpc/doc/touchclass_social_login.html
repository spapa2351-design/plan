먼저 합의할 4가지

이 방향에 동의한 뒤, 아래 상세를 함께 정합니다

아래 네 가지는 이번 라운드에서 “이 틀로 가자”고 정렬하려는 큰 방향입니다. 세부 규칙·예외 처리는 4장에서 팀이 함께 결정합니다.

① 연동 범위
소셜 로그인 방식 (A안)
“Google / Microsoft로 로그인” 버튼 방식. 고객사 IdP를 직접 연동하는 엔터프라이즈 SSO(B안)는 이번 범위에서 제외.
② 사용자 처리
기존 사용자 매칭 전용
이미 테넌트에 등록된 사용자만 로그인. 로그인 시점에 계정을 자동 생성(JIT)하지 않음 — 수강 대상은 관리자가 통제.
③ 식별 키
이메일이 아닌 불변 키
인증·매칭의 기준은 변경 가능한 이메일이 아니라 IdP가 주는 불변 키 (issuer, sub). 이메일은 표시·최초 매칭용 속성.
④ 핵심 변화
테넌트 선택 → ‘인증 후’로 이동
비밀번호는 아이디를 먼저 받아 인증 전에 테넌트를 가렸지만, 소셜은 인증을 마쳐야 신원을 알 수 있음.
01 · 개념 정렬

“소셜 로그인”과 “엔터프라이즈 SSO”는 다릅니다

고객사의 “우리 Workspace 계정을 그대로 쓰고 싶다”는 요구는 두 가지로 해석될 수 있습니다. 이번 범위는 A안(소셜 로그인)으로 정렬하되, 두 개념의 차이를 팀이 같은 의미로 이해하고 시작하는 것이 목적입니다.

이번 범위 ✓

A. 소셜 로그인

  • “Google / Microsoft로 로그인” 버튼 방식
  • OAuth 2.0 / OIDC 표준
  • 이메일·불변키로 기존 사용자에 매칭
  • 구현이 가볍고 빠르게 출시 가능
이번 제외 · 추후 검토

B. 엔터프라이즈 SSO

  • 고객사 도메인 단위로 IdP 직접 연동
  • SAML / OIDC, 도메인 클레이밍 필요
  • 관리자 통제·퇴사자 차단이 강력
  • 구현·운영 부담이 큼 → 후속 단계 검토
A안으로 시작하더라도, 이메일 검증·도메인 확인 같은 안전장치는 B안을 염두에 두고 설계해 두면 후속 확장이 매끄럽습니다. 이 부분은 4장에서 함께 정합니다.
02 · 큰 그림

로그인 흐름은 이렇게 바뀝니다

가장 중요한 변화 한 가지만 기억하면 됩니다 — 테넌트(조직) 선택 단계의 위치. 비밀번호는 인증 전에, 소셜은 인증 후에 테넌트를 가립니다.

03 · 시나리오

인증 후, 후보 테넌트 수에 따라 갈립니다

IdP 인증이 끝나면 “이 사람이 들어갈 수 있는 테넌트”를 산출합니다. 그 개수에 따라 동작이 단순하게 세 갈래로 나뉩니다.

IdP 인증 완료 → 후보 테넌트 산출후보 = 가입된 테넌트 ∩ 소셜 로그인을 허용한 테넌트
0개
안내 화면등록된 계정이 없음 → 관리자 문의 / 다른 계정 / 비밀번호 로그인 유도
1개
바로 진입선택 단계 없이 해당 테넌트로
(단일 테넌트 비밀번호와 동일 경험)
2+개
조직 선택 → 진입인증 후 “조직 선택” 화면 노출
(기존 테넌트 목록 컴포넌트 재사용)
후보 산출 시 가입 여부 뿐 아니라 해당 테넌트가 소셜 로그인을 허용하는지까지 함께 거릅니다. (테넌트별 정책은 4-C 참조)
04 · 드릴다운

함께 고민할 상세 이슈

아래는 “결론”이 아니라 팀이 함께 정해야 할 논의 거리입니다. 각 항목은 방향(제안)과 함께 정할 것(열린 질문)으로 나눠 두었습니다. 펼쳐서 확인하세요.

A아이디 & 사용자 매칭▶

소셜 이메일을 터치클래스 아이디로 그대로 쓸지 / 어떤 키로 사용자를 찾을지

방향(제안)
  • 인증·매칭의 불변 키는 (issuer, sub)로 두고, 이메일은 표시·최초 매칭용 속성으로만 사용 (이메일은 IdP에서 변경될 수 있음).
  • 현재 아이디 체계는 바꾸지 않고, 별도의 매핑 레이어(issuer·sub·email → user·tenant)를 추가하는 방향.
  • 동일 테넌트 내 이메일은 유일하되, 멀티테넌트이므로 서로 다른 테넌트엔 같은 이메일 공존 가능(테넌트 중복의 근원).
함께 정할 것
  • 현재 아이디가 이메일인지 / 사번·username인지? — 이메일이 아니면 “이메일=아이디” 안은 성립하지 않음. (가장 먼저 확인 필요)
  • 고객사가 등록한 이메일과 실제 IdP 이메일이 다를 때의 보완 경로(관리자 초대 매칭 등).
B보안 정책▶

Workspace 계정 사용 시 / 소셜 로그인만 쓸 때 터치클래스 정책을 어디까지 책임지는가

방향(제안)
  • 자격증명 정책은 IdP에 위임 — 비밀번호 복잡도·변경 주기·이력·잠금 등은 Google/MS가 처리(터치클래스가 강제 불가). “Workspace가 알아서 처리” 판단은 이 영역에선 타당.
  • 대신 세션 정책(유효기간·유휴 타임아웃·강제 로그아웃)은 터치클래스가 계속 책임 — IdP와 무관.
  • 소셜 전용 사용자에겐 “비밀번호 변경” 메뉴를 숨기고 “연결된 로그인 수단”을 노출.
함께 정할 것
  • 접근 회수(디프로비저닝): 고객사가 IdP에서 계정을 막아도 기존 세션은 즉시 안 끊김 → 세션을 짧게 둘지, 후속에 SCIM을 검토할지.
  • 증적·컴플라이언스: ISMS-P·계약상 요구가 있다면 “IdP 위임”을 문서로 명시할지 (구체 요건은 보안/법무 검토).
  • MFA·계정 복구: IdP MFA에 의존할지, 비밀번호 재설정이 없는 소셜 전용 사용자의 복구 경로(비상용 비번 허용 여부).
C테넌트 선택 UI/UX▶

인증 후로 옮겨간 테넌트 선택을 어떻게 자연스럽게 처리할지

방향(제안)
  • “조직 선택” 화면은 로고·조직명·내 역할 카드로 구성, 최근 사용 조직을 상단에.
  • 최근 조직 기억(디바이스별)으로 다음 로그인 시 선택 단계 생략 + “조직 전환” 제공.
  • 비밀번호 흐름의 테넌트 목록 컴포넌트를 재사용하되 트리거되는 단계만 다르게.
  • 테넌트별 로그인 정책: 허용 수단은 테넌트(고객사)별 설정으로(예: A사 비밀번호만 / B사 Google만 / C사 둘 다). 후보 산출의 필터로 직결.
함께 정할 것
  • 테넌트 전용 진입 경로(서브도메인·딥링크)로 들어온 경우 선택 단계를 생략할지.
  • 후보 0개일 때 안내 카피·대안(다른 계정/비밀번호) 노출 방식.
D계정 충돌 처리▶

소셜 이메일이 기존 비밀번호 계정과 겹칠 때 (셀프 연결 UI는 추후 개발)

셀프 연결 UI는 추후 개발이지만, 최초 로그인 시 기존 계정과의 매칭은 1차 출시에 필요합니다. 없으면 기존 사용자가 소셜로 들어와도 자기 계정에 못 붙어 기능이 무력화됩니다.
방향(제안)
  • 검증된 이메일(email_verified=true)일 때만 신뢰 — 미검증 이메일로 기존 계정 자동 연결 금지(사전 탈취 방지).
  • 동일 테넌트의 기존 계정과 검증 이메일이 일치하면 서버가 (issuer, sub) 링크를 자동 생성(보이는 “연결 관리” UI만 추후).
  • Google은 hd(도메인), Microsoft는 tid(테넌트) 클레임으로 회사 계정 검증.
함께 정할 것
  • 자동 연결로 갈지, “기존 계정을 찾았습니다 → 확인” 1단계를 넣는 보수적 방식으로 갈지.
  • 개인 계정 vs 회사(work/school) 계정 허용 범위(특히 Microsoft).
05 · 레퍼런스

타 SaaS는 어떻게 풀었나

업계 공통 패턴은 “계정 먼저(account-first), 테넌트는 인증 후 선택” — 우리가 가려는 방향과 정확히 같습니다.

Slack
Google·SSO로 인증한 뒤 그 이메일이 속한 워크스페이스 목록을 보여 선택. 승인 도메인 기반 자동 가입도 제공.
Notion
“Continue with Google/Apple”로 인증 후 워크스페이스 선택. 한 계정이 여러 워크스페이스에 소속되는 구조.
Atlassian
Atlassian 계정으로 인증한 뒤 접근 가능한 사이트(site)를 선택하는 계정 중심 모델.
Figma · Linear
Google 인증 후 워크스페이스를 고르는 동일 패턴. 멀티 워크스페이스 전환을 매끄럽게 제공.
시사점: ① 인증 후 테넌트 선택, ② 마지막 사용 테넌트 기억, ③ 도메인 기반 자동 매핑 — 우리의 멀티테넌트·중복 이메일 상황에 그대로 적용 가능합니다.
06 · 다음 단계

단계적 접근

큰 방향에 정렬되면, 아래처럼 나눠 진행하는 안을 제안합니다. (세부 범위는 논의로 조정)

Phase 0

방향 정렬

본 문서 4가지 방향 합의 + 4장 열린 질문 1차 결정 (특히 아이디 체계 확인).

Phase 1

MVP

Google·Microsoft 소셜 로그인, 검증 이메일로 기존 사용자 매칭, 인증 후 테넌트 선택, 테넌트별 허용 토글, 소셜 전용 정책(비밀번호 UI 숨김), 서버 사이드 자동 연결.

Phase 2

확장

설정 내 셀프 계정 연결 UI(이번에 미룬 기능), 도메인 기반 매핑, SCIM 디프로비저닝, 테넌트별 SSO 강제 등 — B안 방향 검토.

먼저 답이 필요한

열린 질문

현재 아이디 체계는 이메일인가, 사번/username인가? — 매칭 로직과 “이메일=아이디” 가능 여부의 핵심.
소셜 전용 사용자에게 비상용 비밀번호 설정을 허용할 것인가? — IdP 계정 분실 시 복구 경로.
Microsoft 개인 계정도 허용할 것인가, work/school만 허용할 것인가?
퇴사자 차단(디프로비저닝)을 어느 단계에 넣을 것인가? — 세션 길이 정책 / 후속 SCIM.
이메일 충돌 시 자동 연결인가, 1단계 확인인가? — 보안 강도와 UX의 트레이드오프.
터치클래스 소셜 로그인 도입 — 방향 정렬 초안 · 본 문서는 의사결정을 위한 논의 자료이며, 세부 스펙은 팀 논의로 확정됩니다.
